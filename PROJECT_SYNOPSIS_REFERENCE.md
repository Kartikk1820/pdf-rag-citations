## 2. Abstract / Overview

Large Language Models (LLMs) are powerful at answering natural-language questions, but they are
prone to **hallucination** — generating plausible-sounding but factually incorrect or fabricated
information, including fake citations and page numbers. This is a critical problem in domains
like legal, HR, compliance, and policy documentation, where every answer must be traceable back
to an exact source.

This project implements a **Retrieval-Augmented Generation (RAG)** system that answers natural
language questions **strictly from the content of a given set of PDF documents**. Unlike typical
RAG systems where the LLM itself reports the source page (which is unreliable and prone to being
invented), this system is architected so that **the LLM is never trusted to generate citation
metadata**. Instead, the LLM only performs two narrow, verifiable jobs:

1. Decide whether the user's question is answerable from the retrieved text snippets.
2. Report *which* of the numbered snippets (by index) it used to construct the answer.

The actual **document name and page number** attached to every citation are deterministically
pulled from metadata that the system itself recorded during ingestion — **not generated by the
model**. This makes citations "correct by construction": the LLM has no opportunity to invent a
page number because it never produces one. If no retrieved content is relevant enough, or the
model itself reports the question is unanswerable, the system explicitly responds:

> "The information is not available in the supplied documents."

rather than guessing — directly addressing the hallucination problem.

Beyond the citation-correctness contribution, the retrieval step itself goes well past a typical
"embed the question, search a vector DB" RAG demo. The system combines **lexical (BM25) and
dense (embedding) search fused via Reciprocal Rank Fusion**, expands the user's question into
**multiple LLM-generated reformulations** before retrieving, and **reranks the fused candidates
with a cross-encoder** that judges the question and each candidate together — a materially
stronger relevance signal than raw cosine similarity. The cross-encoder's calibrated score, not
the embedding similarity, is what ultimately decides whether a question is answerable from the
corpus at all.

The system is delivered as a **full web application** (Dashboard, Document Library, a streaming
multi-turn Chat screen, an Analytics screen, and a Settings screen) in addition to the original
command-line interface, and runs **entirely on local, free components**:

- **Local, offline, free embeddings and reranking** (fastembed, ONNX runtime — no PyTorch, no
  per-call API cost, works without internet after the one-time model download)
- **Qdrant in embedded mode** — a local on-disk vector index with no server process, container,
  or network port involved
- **Free-tier LLM providers** (OpenRouter and Groq, both OpenAI-API-compatible) for the
  reasoning/answer-generation step
- **Structured JSON-mode LLM calls** validated against a strict schema, with automatic retry and
  JSON-repair logic for robustness
- **Zero infrastructure dependencies** beyond Python itself — no Docker, no Node.js, no database
  server to install or run

## 3. Problem Statement

Organizations and individuals often need to query large sets of PDF documents (employee
handbooks, legal contracts, government policy documents, research papers, manuals, etc.) and get
quick, accurate answers. Two common but flawed approaches exist:

1. **Manual search (Ctrl+F / reading):** Accurate but slow and doesn't scale to many documents or long documents.
2. **Naive LLM usage (e.g., pasting text into ChatGPT or asking an LLM directly):**
   - The LLM may answer using its own pre-trained "world knowledge" instead of the actual
     document content (ungrounded answers).
   - The LLM may **hallucinate** page numbers, section numbers, or document names when asked to
     cite a source — these citations look convincing but are frequently wrong.
   - There's no way to verify, at a glance, which part of the document the answer came from.
   - Simple vector-only retrieval (the common approach in most "chat with your PDF" tutorials)
     frequently misses exact keyword matches (names, IDs, section numbers) that a reader would
     find instantly with Ctrl+F, because embedding similarity is a semantic/paraphrase signal, not
     a lexical one.

**The core problem this project solves:** *How do we let an LLM answer natural-language
questions over a document corpus while guaranteeing that every citation (document + page number)
is actually correct, retrieving the right evidence even when the question's wording doesn't match
the document's wording, and guaranteeing the system refuses to answer when the information
genuinely isn't present in the documents — all packaged as something a non-technical person can
actually use?*

## 4. Objectives

1. Build a pipeline that ingests PDF documents, extracts their text while preserving page-level
   granularity, and stores them in a searchable index.
2. Implement **hybrid retrieval** — semantic (vector) search fused with lexical (BM25, keyword)
   search — so that both paraphrased questions and exact-keyword questions are retrieved well.
3. Improve retrieval precision further with a **cross-encoder reranking** stage, and use its
   calibrated relevance score (not raw cosine similarity) as the "is this corpus even relevant"
   gate.
4. Improve retrieval recall with **LLM-driven query rewriting** (multi-query retrieval), so a
   single oddly-phrased question still finds the right evidence.
5. Use an LLM only for language understanding, relevance judgment, and answer synthesis —
   **never for generating source metadata** — to eliminate citation hallucination.
6. Ensure the system can correctly refuse to answer when a question is out-of-scope or when
   retrieval confidence is too low.
7. Support natural, **multi-turn conversation** (follow-up questions that refer back to earlier
   turns) rather than only independent single-shot queries.
8. Provide a **professional, multi-screen web application** (Dashboard, Document Library, Chat,
   Analytics, Settings) so the system is usable by someone who isn't comfortable with a terminal,
   while keeping the original CLI available.
9. Provide **observability**: log latency, retrieval confidence, and answer/no-match outcomes for
   every question, surfaced on an Analytics screen.
10. Keep the solution **cost-free, dependency-light, and reproducible**: local embeddings and
    reranking (no API cost), free-tier LLM APIs, and an embedded (serverless) vector store — no
    Docker, no Node.js, no database server to install.
11. Ensure correctness through automated unit tests that validate chunking, citation
    construction, the unanswerable-question path, and the streaming decision/narration split —
    without needing live network/LLM calls.

## 5. Scope

**In scope:**
- Text-based (digitally generated) PDFs — i.e., PDFs where text can be extracted programmatically.
- Page-level citation granularity (which document, which page number, and the exact retrieved
  text snippet), with a visible **confidence score** per citation.
- A single unified searchable collection built from all PDFs placed in a designated folder, with
  an optional per-query filter to scope retrieval to a chosen subset of documents.
- Hybrid (BM25 + dense) retrieval with Reciprocal Rank Fusion, LLM-driven query rewriting, and
  cross-encoder reranking.
- Multi-turn conversational context within a session.
- A web application front-end (5 screens) **and** a CLI, sharing the same retrieval/citation core.
- Per-query analytics (latency, confidence, outcome) persisted locally.
- Runtime-configurable retrieval/LLM settings via a Settings screen (persisted to `.env`).

**Out of scope (explicitly stated assumptions/limitations):**
- Scanned/image-based PDFs requiring OCR (Optical Character Recognition) are not supported.
- No multi-user authentication or access control — it is a local, single-user tool (chat history
  and analytics are process-local, not tied to user accounts).
- No fine-tuning of the underlying LLM or the embedding/reranking models; the system relies
  entirely on retrieval + prompting (zero model training involved).
- No incremental ingestion — re-running `ingest` rebuilds the full index from the PDFs currently
  on disk.

## 6. Literature / Background Concepts (for the synopsis's "Existing System" / "Related Work" section)

- **Large Language Models (LLMs):** Neural network models (e.g., GPT, Llama, Gemma) trained on
  vast text corpora that can generate human-like text and answer questions. They have a
  "knowledge cutoff" and can hallucinate facts not present in their training data or the provided context.
- **Retrieval-Augmented Generation (RAG):** A technique (introduced by Lewis et al., 2020,
  Facebook AI Research) that combines a retrieval system (which fetches relevant documents/text
  chunks from an external knowledge base) with a generative language model, so that the model's
  answer is "grounded" in retrieved evidence rather than purely relying on its internal
  parametric memory.
- **Vector Embeddings:** Numerical (vector) representations of text such that semantically
  similar pieces of text are placed close together in vector space. Enables "meaning-based"
  search rather than exact keyword matching.
- **Lexical Search / BM25:** A classical probabilistic term-weighting ranking function
  (Robertson & Zaragoza) that scores documents by exact term overlap with a query, adjusted for
  term frequency and document length. Complements embeddings by catching exact keyword/ID/name
  matches that semantic similarity can miss.
- **Hybrid Search:** Combining lexical and semantic retrieval so each covers the other's blind
  spots. A common fusion technique is **Reciprocal Rank Fusion (RRF)** (Cormack, Clarke & Büttcher,
  2009), which merges multiple ranked lists using only each item's *rank* (not its raw score),
  avoiding the problem of combining incomparable score scales (cosine similarity vs. BM25 score).
- **Cross-Encoder Reranking:** Unlike a dense retriever, which embeds the query and each document
  independently, a cross-encoder (Nogueira & Cho, 2019, and related passage-reranking work) takes
  the query and a candidate **together** as a single input and outputs a relevance score. This is
  computationally heavier (so it is only applied to a small candidate shortlist, after initial
  retrieval) but is a substantially stronger relevance signal.
- **Vector Databases:** Specialized databases (e.g., Qdrant, Pinecone, Weaviate, FAISS,
  Milvus) optimized for storing high-dimensional vectors and performing fast nearest-neighbour /
  similarity search. Many, including Qdrant, also offer an **embedded/serverless mode** that runs
  as a library inside the host process rather than a separate server.
- **Hallucination in LLMs:** A well-documented failure mode where an LLM generates confident
  but factually incorrect, fabricated, or unverifiable content — a major obstacle to deploying
  LLMs in high-stakes or factual domains.
- **Grounding / Citation Verification:** An active research area focused on making LLM outputs
  traceable to verifiable sources, which is the central theme this project addresses practically.

This project can be framed academically as **an applied implementation and engineering solution
to the LLM hallucination/citation-reliability problem**, built on top of a hybrid information
retrieval pipeline, in the context of document-based question answering.

## 7. Proposed System / Methodology

The system has two independent pipelines: an **Ingestion (offline/indexing) pipeline** and a
**Query (online/answering) pipeline** — plus a web application layer on top of the query pipeline.

### 7.1 High-Level Architecture Diagram (textual)

```
========================= INGESTION PIPELINE =========================

   data/*.pdf
        |
        v
  [1] PDF Loader (pypdf)
      - Reads each PDF page-by-page, extracts raw text per page
      - Normalizes whitespace, preserves 1-based page number + source filename
        |
        v
  [2] Chunker
      - Splits each page's text into overlapping chunks (~800 characters, 120-char overlap)
      - "Recursive character splitter": prefers paragraph > line > sentence > word boundaries
      - Chunking happens strictly WITHIN a page boundary, so every chunk carries an exact page number
      - Assigns a unique UUID to every chunk
        |
        v
  [3a] Embedding Model (fastembed — BAAI/bge-small-en-v1.5, 384-d, local/offline)
       -> stored in embedded Qdrant (vector index, on-disk, no server)
  [3b] Same chunks are also persisted to a local JSON file and indexed with BM25
       (rank_bm25, in-process) -- this is the lexical half of hybrid search


========================= QUERY PIPELINE ==============================

   User's natural-language question (+ recent conversation turns, if any)
        |
        v
  [1] Query Rewriting (LLM, JSON mode)
      - Generates 2-3 alternative phrasings of the question (resolving pronouns
        from recent turns, expanding abbreviations, varying vocabulary)
      - Toggle-able; the original question is always included regardless
        |
        v
  [2] Hybrid Retrieval (per phrasing)
      - Dense search: embed the phrasing, cosine-similarity search in Qdrant
      - Lexical search: BM25 score against the persisted chunk corpus
      - Optional metadata filter to restrict search to selected documents
        |
        v
  [3] Reciprocal Rank Fusion (RRF)
      - Every ranked list (dense + lexical, per phrasing) contributes
        weight / (60 + rank) to each candidate's fused score
      - Produces one merged, deduplicated candidate pool, scale-free
        (ranks are combined, not raw scores of different units)
        |
        v
  [4] Cross-Encoder Reranking (ONNX, fastembed, no torch)
      - The question and each fused candidate are scored TOGETHER
        (a materially stronger relevance signal than embedding similarity)
      - Raw logit -> sigmoid -> a 0..1 "confidence" score shown in the UI
        |
        v
  [5] Relevance Gate
      - If the BEST reranked candidate's score is below SCORE_THRESHOLD,
        the question is treated as unanswerable WITHOUT calling the LLM
        (saves cost, and guarantees correctness for clearly out-of-scope questions)
        |
        v
  [6] LLM Decision Call (OpenRouter or Groq, JSON mode)
      - Top-K reranked chunks are presented as a NUMBERED context list
      - The LLM responds with EXACTLY:
            { "is_answerable": true/false, "answer": "...", "used_chunk_indices": [...] }
      - The LLM NEVER outputs a document name or page number -- only snippet
        INDEX numbers referring to the numbered list it was given
        |
        v
  [7] Deterministic Citation Construction
      - For each index the LLM reported using, the app looks up that
        chunk's ACTUAL stored {source, page} metadata (captured during ingestion)
        and the reranker's confidence score, and builds a Citation object
      - Citations cannot be hallucinated: the LLM never produces a page number
      - Duplicates removed, capped at 3; falls back to the top candidate if the
        model names no usable index, so an answer is never shown uncited
        |
        v
  [8] Answer Narration
      - CLI path: the decision call's own "answer" field IS the final text
        (one LLM round-trip -- fast, good enough for a terminal)
      - Web UI path: a SECOND, unconstrained LLM call streams the prose
        answer token-by-token, using the already-decided chunks as context --
        citations are shown to the user before the prose even finishes,
        and the UI feels responsive instead of waiting on one big call
        |
        v
  Final Output: streamed/returned answer text + citations (doc, page, snippet,
  confidence) -- logged to a local analytics store (question, latency, best
  confidence, answered?) for the Analytics screen
```

### 7.2 Why This Architecture Guarantees Citation Correctness (Key Design Insight)

This is the most important intellectual contribution of the project and should be emphasized in
the synopsis:

> Most naive RAG implementations ask the LLM to directly output "Source: document.pdf, Page 7"
> as part of its answer. This is fundamentally unreliable because the LLM is a text generator —
> it can plausibly format a citation-looking string without any actual verified link to where
> the information came from, especially when snippets from multiple pages/documents are mixed
> into the prompt.
>
> This project avoids that failure mode entirely by **separating "what to say" from "where it
> came from."** The LLM's only responsibility regarding sourcing is to pick WHICH of the
> numbered snippets (an index, 0/1/2/3...) it relied on — a much simpler and far more reliable
> task than generating exact page numbers from memory. The actual page number and filename are
> never shown to the LLM as something it needs to reproduce; they are attached afterward by the
> application code using the index as a lookup key into data the system already knows to be true
> (because it recorded it during ingestion). This makes citations **"correct by construction"**
> rather than "hopefully correct because the model tried."

### 7.3 Why Hybrid Search + Reranking, Not Just Embeddings (Second Key Design Insight)

> Dense embeddings excel at paraphrase/semantic matches ("leave policy" ~ "time-off rules") but
> routinely miss exact keyword hits — product codes, names, section numbers — because those don't
> have a strong semantic "meaning" to embed. BM25 catches exactly those cases. Rather than pick
> one, the system runs both and fuses their rankings with Reciprocal Rank Fusion, which only needs
> each ranker's *rank order*, not its raw score, so two incomparable scoring systems (cosine
> similarity vs. a BM25 score) can be combined safely.
>
> The fused candidates then go through a cross-encoder, which reads the question and a candidate
> **together** instead of comparing two independently-computed embeddings. This is a stronger
> relevance signal, and the project uses it for something beyond just reordering results: the
> cross-encoder's score is the gate that decides whether the corpus can answer the question at
> all, replacing the original design's reliance on raw embedding cosine similarity for that
> decision.

## 10. Key Algorithms / Logic Explained

### 10.1 Recursive Character Text Splitting (Chunking Algorithm)
- Goal: break long page text into fixed-size chunks (~800 chars) without cutting sentences/words
  awkwardly, while keeping a small overlap (~120 chars) between consecutive chunks so that
  context near chunk boundaries isn't lost.
- Approach: for each window of text up to `chunk_size`, search backward from the end of the
  window for the **coarsest available separator** in a priority order: paragraph break (`\n\n`)
  → line break (`\n`) → sentence end (`. `) → word boundary (` `). If found, cut there instead of
  at the raw character limit.
- Guarantees forward progress (an explicit `max(end - overlap, start + 1)` step) to avoid
  infinite loops on adversarial inputs — regression-tested explicitly.
- Chunking is always scoped to a single page's text, never spanning two pages — this is what
  makes exact page-level citation possible later.

### 10.2 Hybrid Retrieval: Dense + BM25 Fused by Reciprocal Rank Fusion
- **Dense side:** the question (and each LLM-generated rewrite) is embedded with the same model
  used for documents, and Qdrant returns the top-K nearest neighbours by cosine similarity.
- **Lexical side:** the same query text is scored against every chunk with BM25 (term-frequency /
  inverse-document-frequency style scoring over tokenized text), returning its own top-K list.
- **Fusion:** for every ranked list produced (one dense + one lexical list *per query
  phrasing*), each item at rank `r` contributes `weight / (60 + r)` to a running score, keyed by
  chunk ID. The `60` is the standard RRF damping constant; `weight` lets lexical vs. dense
  contribution be tuned (`HYBRID_BM25_WEIGHT`, default 0.4). Because RRF only looks at rank
  position, it fuses rankers with completely different, non-comparable score scales (a cosine
  similarity in [-1, 1] vs. an unbounded BM25 score) without needing to normalize either.
- The highest-fused-score candidates (`RETRIEVAL_K`, default 20) go on to reranking.

### 10.3 Cross-Encoder Reranking and the Relevance Gate
- A cross-encoder (`Xenova/ms-marco-MiniLM-L-6-v2`, run locally via ONNX through `fastembed` — no
  PyTorch) takes the question and each fused candidate **as a single joint input** and outputs a
  raw relevance logit, which is passed through a sigmoid to get a 0–1 score.
- This is a strictly stronger relevance signal than comparing two independently-computed
  embeddings, because the model can directly attend between the question and the candidate text.
- The top `TOP_K` (default 5) reranked candidates are what get shown to the LLM. The **single
  highest reranked score** is also what the system checks against `SCORE_THRESHOLD` to decide
  whether to even call the LLM — replacing the original design's reliance on raw embedding cosine
  similarity for that decision with a materially more reliable one.

### 10.4 Query Rewriting (Multi-Query Retrieval)
- Before retrieval, the question (plus recent conversation turns, if any) is sent to the LLM with
  a prompt asking for 2–3 alternative phrasings — resolving pronouns, expanding abbreviations,
  varying vocabulary — returned as a validated JSON list.
- Every phrasing (including the original) is run through hybrid retrieval independently, and all
  resulting rankings are fused together in the same RRF step described above. This increases the
  chance that at least one phrasing's wording overlaps well with the document's actual wording.
- Implemented defensively: if the rewrite call fails for any reason, it simply returns no extra
  phrasings and retrieval proceeds with the original question alone.

### 10.5 Structured, Schema-Validated LLM Output (Reliability Pattern)
1. Request JSON-mode output from the LLM API (`response_format={"type": "json_object"}`).
2. Attempt to `json.loads()` the raw response.
3. If that fails (malformed JSON), attempt automatic repair via `json_repair` before parsing again.
4. Validate the parsed object against a strict `pydantic` schema.
5. If validation still fails, perform exactly **one** bounded retry with an explicit correction
   instruction appended to the prompt.
6. Separately, `tenacity` wraps the raw API call itself with up to 3 attempts (fixed 2-second
   wait) specifically for *transient* transport errors (rate limiting, connection errors) —
   distinct from the JSON-validity retry logic above. This pattern is reused for both the
   grounding decision call and the query-rewrite call.

### 10.6 Deterministic Citation Assembly
1. The LLM returns a list of integer indices (`used_chunk_indices`) referring to position in the
   numbered snippet list it was shown.
2. The app looks up each index's corresponding `Candidate`, and reads off its `source`/`page`
   (recorded during ingestion, never touched by the LLM) and its cross-encoder confidence score.
3. Invalid indices are silently skipped; duplicate `(source, page)` pairs are removed; citations
   are capped at 3.
4. If the model answers but names zero usable indices, the system falls back to citing the
   single highest-reranked candidate, so an answer is never shown without a citation.

### 10.7 Decoupled Decision and Narration, with Streaming
- The *decision* (is this answerable? which chunks?) and the *narration* (the prose shown to the
  user) are deliberately two different LLM calls in the web path:
  1. A JSON-mode call decides answerability and chunk usage — this is what citations are built
     from, so citations are known and can be displayed **before any prose text appears**.
  2. If answerable, a second, unconstrained (non-JSON) call streams the final prose token-by-token
     using the same already-selected chunks as context.
- The CLI path uses only the first call's own `answer` field directly (one round-trip, cheaper and
  fast enough for a terminal where streaming doesn't matter as much).
- Streaming is implemented as newline-delimited JSON events (`{"kind": "citations"/"token"/"done"/"error"}`)
  over a chunked HTTP response, consumed in the browser with `fetch` + a `ReadableStream` reader —
  simpler to implement than strict Server-Sent-Events framing while still giving real token-by-
  token UX, and it works with a POST body (which a native `EventSource` cannot send).

## 13. Assumptions and Constraints

- Input PDFs are **text-based**; scanned/image-only PDFs are not supported (no OCR step).
- Citation granularity is at the **page level**.
- All ingested PDFs live in a single shared collection; re-running `ingest` rebuilds it from
  scratch (no incremental/delta updates).
- Embeddings and reranking run **locally** (no external API, no per-call cost); the LLM is the
  only component that requires network access and an API key.
- Qdrant's embedded mode locks its storage directory to **one process at a time** — the CLI and
  the web app should not be run concurrently against the same storage folder.
- Chat history and analytics are **process-local** (an in-memory list and a local SQLite file
  respectively) — this is a single-user local tool, not a hosted multi-tenant service.
- Free-tier LLM model availability on OpenRouter/Groq changes over time; the active model can be
  changed from the Settings screen or `.env` without any code change.

## 14. Testing Strategy

- **Framework:** `pytest`.
- **Design principle:** tests run **completely offline** — no real network calls, no live LLM
  calls, no running vector store required — achieved by monkeypatching the retrieval and LLM
  boundaries (`rag.retrieval.candidates`, `rag.call_structured_answer`, `rag.llm.stream_chat`)
  with controlled fake implementations.
- **Coverage includes:**
  1. Chunking correctness and the early-separator infinite-loop regression.
  2. Citation correctness: given fabricated retrieval candidates (with a known confidence score)
     and a fabricated LLM decision, the final citation's source/page/confidence is asserted to
     match the candidate's stored data — directly validating the "citations can't be
     hallucinated" design claim.
  3. Unanswerable-question handling, both when the LLM reports `is_answerable: false` and when no
     candidate clears the relevance threshold (asserting the LLM is **never even called** in the
     latter case).
  4. Output sanitization: stray bracketed index markers leaked into the prose are stripped.
  5. Fallback-citation behaviour when the model names no usable snippet index.
  6. The streaming path: `stream_answer()` is asserted to emit the citations event before any
     token event, and a `done` event last, with the concatenated tokens matching the mocked
     narration output.
- Runnable with a single command: `pytest -q`.

## 15. Advantages of This System

1. **Hallucination-resistant citations** — citations are structurally guaranteed to be accurate
   because the LLM never generates them.
2. **Stronger retrieval than embeddings alone** — hybrid BM25+dense search with Reciprocal Rank
   Fusion catches both paraphrased and exact-keyword questions; cross-encoder reranking and
   LLM-driven query rewriting push relevance further still.
3. **A reliable "I don't know"** — the relevance gate uses a calibrated cross-encoder score, not
   raw cosine similarity, to decide whether to even attempt an answer.
4. **Low/zero operating cost, zero infrastructure** — local, free embeddings and reranking;
   free-tier LLM APIs; an embedded (serverless) vector store. No Docker, no Node.js, no database
   server — `pip install` and run.
5. **Provider-agnostic LLM layer** — both supported providers expose an OpenAI-compatible API, so
   switching providers is a configuration change, not a code change.
6. **Deterministic, testable core logic** — the safety-critical parts (citation construction, the
   unanswerable path, the streaming event ordering) are fully unit-tested without live services.
7. **A genuinely usable interface** — a professional multi-screen web application (not just a
   terminal), with observability (Analytics) and runtime tuning (Settings) built in, while the
   original CLI remains available.
8. **Responsive UX despite a multi-step pipeline** — citations appear as soon as they're decided,
   and the prose answer streams token-by-token, rather than the user staring at a blank screen
   while query rewriting, hybrid search, reranking, and two LLM calls all happen.

## 16. Limitations

1. No OCR support — cannot process scanned/image-based PDFs.
2. Page-level (not paragraph/line-level) citation granularity.
3. Conversation history and analytics are process-local, not persisted across app restarts or
   shared across multiple users/devices.
4. No concurrent multi-user support, and the embedded vector store only allows one process to
   access its storage directory at a time.
5. Answer quality is still bounded by the chosen LLM's reasoning ability (free-tier models can be
   weaker than larger paid models) and by retrieval actually surfacing the relevant chunk — a
   limitation inherent to any RAG system, though mitigated here by hybrid search and reranking.
6. Free-tier LLM model availability on OpenRouter/Groq changes over time, occasionally requiring
   a model-name update (now doable from the Settings screen, without redeploying).
7. Query rewriting and the two-call streaming narration mean answering a question can involve up
   to 3 LLM calls (rewrite, decision, narration) instead of 1 — slightly higher latency and
   free-tier quota usage in exchange for better retrieval recall and perceived responsiveness.

## 17. Future Scope / Possible Enhancements

1. Add OCR support (e.g., via `pytesseract` or a vision-LLM) to handle scanned PDFs.
2. Support incremental ingestion (add/update/remove individual documents without rebuilding the
   entire index).
3. Add multi-user support with authentication and per-user document collections/history.
4. Support additional citation granularity (paragraph- or sentence-level highlighting).
5. Add a systematic evaluation harness (e.g., RAGAS-style metrics: faithfulness, answer
   relevance, context precision/recall) to measure retrieval and answer quality against a
   labeled question set, beyond the current latency/confidence logging.
6. Add support for other document formats (Word, HTML, plain text, PowerPoint).
7. An inline PDF.js viewer on the Chat screen (highlighting the exact cited passage on the page)
   instead of linking out to the browser's native PDF viewer.
8. A feedback mechanism (thumbs up/down per answer) feeding back into retrieval tuning.
9. Export a conversation or an analytics period as a shareable report (PDF/HTML) directly from
   the web app.

## 18. Conclusion

This project demonstrates a practical, cost-free, and architecturally sound solution to one of
the most significant trust problems in applied LLM systems: **unreliable citations** — while also
demonstrating a materially stronger retrieval pipeline than a typical single-vector-search RAG
demo. By strictly separating the LLM's role (language understanding and relevance judgment) from
the application's role (ground-truth metadata bookkeeping), the system guarantees that every
citation shown to a user is traceable to real, stored document metadata — never to a model's
guess. Hybrid search with Reciprocal Rank Fusion, LLM-driven query rewriting, and cross-encoder
reranking together make retrieval itself substantially more reliable than cosine similarity alone,
and that same cross-encoder confidence is what decides whether the system should even attempt an
answer. Packaged as a professional, multi-screen web application with built-in observability and
runtime configuration — deployable with nothing beyond Python — the system is directly applicable
to real-world domains where incorrect information with a false sense of verifiability (a
fake-but-confident citation) can be more dangerous than no answer at all, such as HR policy
lookup, legal document review, compliance checks, and internal knowledge-base question answering.
